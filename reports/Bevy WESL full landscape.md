# Bevy Bets Its Shaders on WESL

As of October 2026, WESL is Bevy's official shader language: **Bevy 0.20 (released October 8, 2026) made WESL an unconditional, always-on part of every Bevy app**, deleting the engine's long-lived private "Custom Bevy Extended WGSL" dialect and its naga_oil preprocessor in the process ([Bevy 0.20 release notes](https://bevy.org/news/bevy-0-20/), [migration guide](https://bevy.org/learn/migration-guides/0-19-to-0-20/)). That closes an roughly 18-month evaluation that began when experimental `.wesl` loading landed behind a cargo feature in Bevy 0.16 (April 2025), and it is the single strongest adoption signal a language that started as a GitHub spec in May 2024 could have received. WESL itself — the "WebGPU Enhanced Shading Language," a **strict superset of WGSL that transpiles down to vanilla WGSL before anything reaches the GPU** — stays deliberately small (stable imports, `@if` conditional translation, npm/cargo packaging) and deliberately independent of Bevy, maintained by the cross-project `webgpu-tools` org led by Mathis Brossier with Bevy developers contributing directly upstream ([wesl-lang.dev](https://wesl-lang.dev/), [wesl-rs README](https://github.com/webgpu-tools/wesl-rs)). Practically, using WESL today means writing `.wesl` files that Bevy's asset pipeline links automatically, with the wgsl-analyzer language server providing IDE support. Outside Bevy, adoption is real but thin — the Balaur engine, the LYGIA shader library, a growing tool suite, and **610k crates.io downloads** — and the long game is upstreaming WESL's ideas into W3C WGSL itself, a process already bearing fruit with the **WGSL namespaces proposal merged in September 2026** ([gpuweb PR #7310](https://github.com/gpuweb/gpuweb/pull/7310)).

## A 20-kilobyte transpiler patches WGSL's missing modularity

WESL ("WebGPU Enhanced Shading Language," pronounced "weasel") exists because WGSL, the standard WebGPU shading language, has no imports, no conditional compilation, and no packaging. The spec frames WESL as "a modestly improved, practical variant of WGSL… WESL should feel like WGSL with a few useful things added," and its core architectural promise is invisibility: **all WESL enhancements are translated to vanilla WGSL before being passed to WebGPU calls like `createShaderModule()`**, so engines like Dawn and wgpu never know WESL exists ([Spec About](https://wesl-lang.dev/spec/README.html)). The project began on **May 8, 2024**, when the GitHub org now called `webgpu-tools` (formerly `wgsl-tooling-wg`) was created with the spec repository, followed by the Rust compiler `wesl-rs` in August 2024 ([GitHub API repo data](https://github.com/webgpu-tools), [wesl-rs README](https://github.com/webgpu-tools/wesl-rs)). Its two leads — Lee Mighdoll (npm WGSL tooling lineage) and Mathis Brossier, a Linköping University PhD student publishing as `k2d222` — built it explicitly to do "what naga_oil does for Bevy, but in a framework-agnostic way," and they design features on WGSL's own reserved words (like `import`) so each one can serve as a literal proposal for future standard WGSL ([Designing.md](https://github.com/webgpu-tools/wesl-spec/blob/main/Designing.md)).

The shipped, stable feature set is narrow by design. **`import` statements** (with `package::`, `super::`, and `constants::` path prefixes) pull declarations from other modules, with lazy linking and dead-code stripping so only transitively-referenced modules are emitted; **`@if`/`@elif`/`@else` attributes** conditionally include declarations, statements, struct members, and function parameters based on host-provided flags, with unused branches stripped from the output; and **packaging** publishes shader libraries to npm and cargo via a `wesl.toml` manifest ([WESL Features doc](https://wesl-lang.dev/docs/WESL-Extensions.html), [llms.txt](https://wesl-lang.dev/llms.txt)). Const injection, virtual modules, CPU evaluation (`eval`/`exec`), and generics (via experimental `@type` attributes, with the spec still living on a fork branch) sit behind cargo feature flags, while visibility keywords and wildcard imports are specified but **rejected by both shipped linkers** — a documented usability trap ([docs.rs/wesl 0.6.0](https://docs.rs/wesl/latest/wesl/), [llms.txt](https://wesl-lang.dev/llms.txt)). The whole language is versioned by Rust-style "editions," and the current one is still labeled **`2026_pre`** — pre-stable ([llms.txt](https://wesl-lang.dev/llms.txt)).

Under the hood, WESL is a classic transpiler, not a text preprocessor: parse → resolve/link modules → apply passes (conditional translation, name mangling) → pretty-print the syntax tree back to canonical WGSL, with a sourcemap module mapping output back to `.wesl` sources ([docs.rs/wesl 0.6.0](https://docs.rs/wesl/latest/wesl/)). There are two independent implementations — `wesl-rs` (crate `wesl`, **v0.6.0 released October 4, 2026**, with C bindings) and `wesl-js` (TypeScript) — and the Rust parser is a **LALR(1) grammar written directly from the WGSL specification** via lalrpop, a constraint the project keeps deliberately so the grammar stays upstreamable; the JS linker is more permissive ([docs.rs/wgsl-parse 0.6.0](https://docs.rs/wgsl-parse/latest/wgsl_parse/), [wesl-rs issue #162](https://github.com/webgpu-tools/wesl-rs/issues/162)). The linkers are **under 20 KB (Brotli), run at over 250,000 lines/second single-threaded (~5 ms for a 1,400-line shader), and are marketed as embeddable in editors** ([llms.txt](https://wesl-lang.dev/llms.txt)).

## Bevy spent a decade hand-rolling what WGSL lacks

Bevy's interest in WESL is not opportunistic — it is the endpoint of a decade-long, self-inflicted preprocessor story. Because WGSL never shipped imports or conditionals, Bevy built its own extended WGSL dialect on top of **naga_oil** (a bevyengine-org crate), with `#import` statements, `#ifdef` blocks, `#{MATERIAL_BIND_GROUP}` placeholders for bind-group indices, and `ShaderDefVal` keyword injection for pipeline specialization ([Bevy 0.16 release notes](https://bevy.org/news/bevy-0-16/)). Throughout, **Naga — wgpu's shader translator — remained the "last stop"**: every dialect, private or standard, had to compile down to WGSL before touching a GPU, and Naga's limits directly gated Bevy features, as when WebGL2 lacked screen-space reflections and depth-of-field because Naga mis-generated depth-texture sampling in Bevy 0.14 ([Bevy 0.14 release notes](https://bevy.org/news/bevy-0-14/)).

The deprecation of that private dialect was staged. Bevy 0.13 (February 2024) removed the naga_oil dependency from `bevy_pbr`, shrinking its blast radius ([Bevy 0.13 release notes](https://bevy.org/news/bevy-0-13/)). **Bevy 0.16 (April 24, 2025) shipped experimental WESL support** — `.wesl` file loading gated behind the opt-in `shader_format_wesl` cargo feature, via PR #17953 by rendering maintainer @tychedelia, merged March 9, 2025 — while candidly admitting the overlap: Bevy had "its own extended version of WGSL," and WESL extended WGSL "often in ways similar to Bevy's approach" ([Bevy 0.16 release notes](https://bevy.org/news/bevy-0-16/), [PR #17953](https://github.com/bevyengine/bevy/pull/17953)). The decisive infrastructure move came in **Bevy 0.17 (~September 2025), which extracted `Shader`, `ShaderRef`, `ShaderDef`, and `ShaderCache` out of `bevy_render` into a dedicated `bevy_shader` crate** and introduced composable specialization (the `Specializer` trait and `Variants<T, S>` keyed cache) — putting the entire shader-source pipeline in one minimal crate so the eventual dialect swap became a single-crate change ([0.16→0.17 migration guide](https://bevy.org/learn/migration-guides/0-16-to-0-17/)). Crucially, Bevy's specialization machinery was kept orthogonal to the source language: `ShaderDefVal` and pipeline variants keyed by (Shader, ShaderDefVal) pairs survived the WESL switch intact, meaning the engine's variant-caching layer never had to change ([docs.rs/bevy_shader](https://docs.rs/bevy_shader/latest/bevy_shader/)).

## Bevy 0.20 makes WESL unconditional for every app

The evaluation ended with a full commitment. Bevy's WESL working group formed in May 2025 asking "Will WESL be enough for Bevy's needs?" ([This Week in Bevy, 2025-05-05](https://thisweekinbevy.com/issue/2025-05-05-new-working-groups-wesl-first-party-tilemaps)); **Bevy 0.19 (June 19, 2026) endorsed WESL as "the shader language of choice for Bevy"** and announced the internal shader port ([Bevy 0.19 release notes](https://bevy.org/news/bevy-0-19/)); and PR #25088 "Migrate to WESL" — opened July 21, merged August 5, 2026, by @tychedelia and @BenjaminBrienen — delivered the switch in **Bevy 0.20, released October 8, 2026** ([Bevy 0.20 release notes](https://bevy.org/news/bevy-0-20/), [PR #25088](https://github.com/bevyengine/bevy/pull/25088)). In 0.20, **the naga_oil preprocessor is gone, the `shader_format_wesl` feature is gone (WESL is always enabled), the custom dialect is deleted, and GLSL input was removed outright**; all of Bevy's own shaders are now written in WESL, while plain WGSL files with no preprocessor directives keep working because WESL is a strict superset ([0.19→0.20 migration guide](https://bevy.org/learn/migration-guides/0-19-to-0-20/)). The integration is deep: `bevy_shader` 0.20 carries a **hard, non-optional dependency on `wesl ^0.6.0` with the `naga-ext` feature** (for Naga/wgpu-specific extensions standard WGSL lacks), and the pipeline runs `.wesl` asset → `ShaderLoader` → `ShaderResolver` (a WESL import resolver mapping module paths to crate or asset sources) → `ShaderCache` (composing final WGSL with shader defs inlined, tracking import resolution) → wgpu/Naga ([docs.rs/bevy_shader](https://docs.rs/bevy_shader/latest/bevy_shader/), [bevy_shader Cargo.toml](https://raw.githubusercontent.com/bevyengine/bevy/main/crates/bevy_shader/Cargo.toml)). Bevy 0.20 also shipped wgsl-analyzer LSP support, closing the tooling gap that @tychedelia had flagged as the main shader pain point back in 2024 ([Bevy 0.20 release notes](https://bevy.org/news/bevy-0-20/), [discussion #14823](https://github.com/bevyengine/bevy/discussions/14823)).

One nuance matters for "official": **WESL is official *for* Bevy but not *of* Bevy**. A search of the bevyengine GitHub org finds zero WESL repositories; the language and compiler live in the independent `webgpu-tools` org, where **Mathis Brossier holds 687 of roughly 900 wesl-rs commits** and Bevy-side developer Benjamin Brienen (whose projects list includes bevy and wgsl-analyzer) is the third-largest contributor with 56 commits ([bevyengine org search](https://github.com/orgs/bevyengine/repositories?q=wesl), [contributors API](https://api.github.com/repos/webgpu-tools/wesl-rs/contributors)). No public funding arrangement was found — Bevy's support is in-kind contributor time and joint language design, the same arm's-length-but-converged posture it has toward WGSL and wgpu itself. Bevy lead cart framed it early in the 0.16 launch video as "an early community-wide effort to extend WGSL… super notable that this will also lead to better language server support in your editor" ([Bevy 0.16 launch video](https://www.youtube.com/watch?v=l13mPxDvKLQ)), and the 0.20 notes state the doctrine plainly: adopting "a common standard where we can pool resources on language improvements, module ecosystems, and IDE tooling" beats maintaining a private dialect ([Bevy 0.20 release notes](https://bevy.org/news/bevy-0-20/)). Post-release maintenance is visibly active — a steady stream of merged PRs through September–October 2026 updated the crate to wesl 0.6, fixed web-platform 404s on shader imports, and ported doc snippets to WESL syntax ([GitHub PR search](https://github.com/bevyengine/bevy/pulls?q=wesl)).

## Day-to-day use is a rename, an import, and a language server

For a Bevy 0.20 developer, "adding WESL" is a non-event: write a `.wesl` file, load it through `AssetServer`/`ShaderRef`, and the engine compiles it at load time — the official `shader_material` example now imports `bevy_pbr::render::forward_io::VertexOutput` and a sibling module via `import super::custom_material_import::COLOR_MULTIPLIER;` ([Bevy shader-material example](https://bevy.org/examples/shaders/shader-material)). Import paths resolve to a crate if one of that name exists, otherwise to an asset path, and `embedded://` shaders are importable at their crate path ([0.19→0.20 migration guide](https://bevy.org/learn/migration-guides/0-19-to-0-20/)). Migrating an existing shader is mechanical:

| Old Bevy dialect | WESL (Bevy 0.20) |
|---|---|
| `#import bevy_pbr::forward_io::VertexOutput` | `import bevy_pbr::render::forward_io::VertexOutput;` |
| `#ifdef X` | `@if(X)` (plus `@elif`/`@else`) |
| `#{MATERIAL_BIND_GROUP}` placeholder | `@binding(constants::MATERIAL_BIND_GROUP)` |
| `#define_import_path` | removed — file paths define modules |
| `.wgsl` extension | rename to `.wesl` |

Integers and unsigned shader defs become readable as `constants::NAME`, and boolean defs become conditional-compilation flags — moving bind-group placeholders from magic textual substitution to ordinary WGSL constants that standard tooling can parse ([0.19→0.20 migration guide](https://bevy.org/learn/migration-guides/0-19-to-0-20/)). Outside Bevy, the `wesl` crate exposes `Compiler::default().compile("shader.wesl")` returning a `CompileResult` whose syntax tree stringifies to WGSL, a `build.rs` workflow (`write_artifact` + `include_wesl!`) for embedded shaders, and a `wesl-cli` binary with `check`, `compile`, `eval`, `exec`, and `package` subcommands ([docs.rs/wesl 0.6.0](https://docs.rs/wesl/latest/wesl/), [wesl-cli](https://docs.rs/crate/wesl-cli/latest)). Editor support is genuinely first-class: **wgsl-analyzer — a rust-analyzer-style LSP for WGSL/WESL with 718 GitHub stars — pairs a VS Code extension with ~25,500 installs and a Zed extension with 52,670 downloads**, offering cross-module go-to-definition, inlay hints, resilient multi-error diagnostics, and a formatter; WGSL Studio adds previews and GPU test running, and play.wesl-lang.dev translates WESL live in the browser ([wgsl-analyzer GitHub](https://github.com/wgsl-analyzer/wgsl-analyzer), [VS Code Marketplace](https://marketplace.visualstudio.com/items?itemName=wgsl-analyzer.wgsl-analyzer), [Zed extension](https://zed.dev/extensions/wgsl-wesl)).

The friction points are those of an ~18-month-old toolchain. **Debugging is the weakest link**: WESL-level compile errors render rustc-style with source spans, but no source confirms that runtime naga/wgpu validation errors get remapped back to `.wesl` line numbers — the practical escape hatch is dumping the composed WGSL with `wesl compile` ([wesl-cli docs](https://docs.rs/crate/wesl-cli/latest)). Version churn is real — the crate went **0.4.0 → 0.6.0 in five months** with `bevy_shader` hard-pinning a specific minor version — and documentation lags the API (the official Getting-Started page still shows the older `Wesl::new` API, and the docs site still calls wgsl-analyzer "coming soon" while Bevy 0.20 ships it) ([wesl-cli releases](https://docs.rs/crate/wesl-cli/latest), [Getting Started Rust](https://wesl-lang.dev/docs/Getting-Started-Rust)). The LR(1) parser once rejected valid WGSL that the JS linker accepted (issue #162, resolved December 2025 by amending the spec grammar), hot-reload of `.wesl` import graphs is undocumented, and third-party crates are mid-migration — particle plugin bevy_enoki shipped its WESL-based 0.8.0 just three days after Bevy 0.20 ([wesl-rs issue #162](https://github.com/webgpu-tools/wesl-rs/issues/162), [lib.rs/bevy_enoki](https://lib.rs/crates/bevy_enoki)). Independent migration commentary captures the cost bluntly: "a project that treated Bevy's preprocessor features as a stable local language needs to own a real conversion step now" ([Emin Budak, Bevy 0.20 migration guide](https://eminbudak.com/blog/bevy-0-20-migration/)).

## Adoption clusters around one flagship — and WGSL is waking up

Bevy is by far WESL's anchor user, and the download numbers should be read with that in mind: **610,410 total crates.io downloads (414,229 recent) are heavily inflated by Bevy's dependency graph**, while the npm package's ~8,080 monthly downloads are a fairer proxy for independent web adoption ([crates.io API](https://crates.io/api/v1/crates/wesl), [npm API](https://api.npmjs.org/downloads/point/last-month/wesl)). The verified second tier is small but real: the **Balaur engine builds its shaders with WESL** ([Balaur devlog 7](https://www.reddit.com/r/rust_gamedev/comments/1wmeig5/balaur_devlog_7_shaders_and_materials)), the **LYGIA shader library documents WESL static linking** for its WebGPU port ([lygia README_WebGPU](https://github.com/patriciogonzalezvivo/lygia/blob/main/README_WebGPU.md)), `bevy-wgsl` repackages all of Bevy's shaders as an importable WESL package so `import bevy_pbr::…` works in non-Bevy tools ([bevy-wgsl](https://github.com/webgpu-tools/bevy-wgsl)), and community bindings exist for Python (wesl-py) and even a Go compiler reimplementation ([PyPI](https://pypi.org/project/wesl-py/), [r/golang thread](https://www.reddit.com/r/golang/comments/1tncffs/wgsl_extension_language_wesl_compiler)). Institutional legitimacy has accrued quickly: the official webgpu.org homepage lists WESL among developer tools, Khronos' SIGGRAPH 2025 BOF slides mention it, and it has spoken at the Khronos Shader Languages Symposium (February 2026), GDC 2026, and TU Wien ([webgpu.org repo](https://github.com/webgpu/webgpu.org), [Khronos SIGGRAPH slides](https://www.khronos.org/assets/uploads/developers/presentations/WebGL%2BWebGPU_SIGGRAPH_2025.pdf), [Khronos symposium page](https://www.khronos.org/developers/linkto/wesl-a-pioneer-language-for-webgpu)). No shipped game publicly citing WESL exists yet — Bevy 0.20 is only two weeks old.

The standards community's reception is the most interesting signal. gpuweb/gpuweb carries a dedicated **"WESL" issue label**, WGSL editor David Neto has given editorial feedback on WESL's `@if` design, Dawn and Bevy contributors have engaged on it, and WESL co-lead Mighdoll committed in September 2026 to bringing the updated conditions design "for the committee to track progress" ([gpuweb #5140](https://github.com/gpuweb/gpuweb/issues/5140)). Meanwhile the competition splits cleanly into *replace WGSL* — NVIDIA's Slang, whose WGSL backend still documents "No" for ray tracing, mesh shaders, tessellation, and geometry shaders, and Rust-GPU, which added a WGSL transpile target in April 2026 — versus *patch WGSL*, where WESL's niche is being the only path that keeps WGSL-identical semantics with tool-visible modularity ([Slang WGSL target docs](https://docs.shader-slang.org/en/stable/external/slang/docs/user-guide/a2-03-wgsl-target-specific.html), [Rust-GPU changelog](https://github.com/Rust-GPU/rust-gpu/blob/main/CHANGELOG.md), [WESL Imports spec](https://wesl-lang.dev/spec/Imports)). The first serious encroachment on WESL's turf came from inside the house: **former WGSL editor dan sinclair merged a native WGSL namespaces proposal on September 16, 2026**, and an open proposal from Godot's Robert Colton argues for API-level module linking instead of host-side preprocessing ([gpuweb PR #7310](https://github.com/gpuweb/gpuweb/pull/7310), [gpuweb #5456](https://github.com/gpuweb/gpuweb/issues/5456)). The main risks are correspondingly clear: **one developer holds roughly 75% of compiler commits**; the spec edition is still `2026_pre` with acknowledged spec-vs-implementation drift; and by design WESL has zero browser or Dawn support, capping it as a build-time layer. The project's own base-case logic, extended: WESL plausibly remains the de-facto module system for WGSL through ~2028, because browser-native imports ship in no browser today and the tooling moat compounds — but if the WebGPU CG advances namespaces and a conditional mechanism to experimental-in-Dawn status, WESL's remaining roadmap (generics, namespaces, auto-bindings) becomes migration liability rather than feature ([wesl-rs README](https://github.com/webgpu-tools/wesl-rs), [llms.txt](https://wesl-lang.dev/llms.txt)).

## Conclusion

The Bevy 0.20 migration reframes what WESL actually is: not a rival language and not a preprocessor, but a **bet that shader modularity belongs to the ecosystem rather than to any engine** — a bet Bevy just made non-theoretical by deleting its own decade-old dialect and hard-pinning the community compiler into every app it ships. The deeper irony of the "superset then standardize" strategy is that it is working, and success is its own terminal state: every WESL feature that lands in WGSL (namespaces already have a merged proposal) retires a line of WESL's value proposition. What survives that convergence is not the syntax but the scaffolding — the npm/cargo packaging layer, the conformance suite, the analyzer, and the habit of treating shaders as libraries — which is precisely how bundlers outlived the CSS features they were written to patch.

The second, less-discussed implication is concentration risk as a design feature. Bevy has knowingly correlated its shader pipeline with a single academic maintainer's compiler, hedging the exposure by embedding its own engineer (Brienen) as the project's third-largest contributor — a human bridge standing in for institutional funding that does not publicly exist. Whether that model scales past Bevy is the question 2027 answers: if a second major engine adopts WESL on its own merits, the webgpu-tools org becomes the neutral meeting ground WGSL's process has always lacked; if adoption stalls at Bevy plus Balaur, WESL will be remembered as the very good private dialect Bevy almost didn't have to maintain alone.
